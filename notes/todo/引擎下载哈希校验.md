## 关键事实（2026-11-25 实测）

| 事实 | 依据 |
|---|---|
| GitHub 对 gdpm 要下载的 zip **100% 提供 digest** | `godot@4.7.2-stable` 18/18、`godot-builds@4.8-beta5` 76/76，格式 `sha256:<hex>` |
| Worker **已经拿得到** digest | `fetchRelease()` 返回完整 release JSON（`asset.digest` 在内），CF 缓存 1h |
| 中继路径含完整三元组 | `/gh/godotengine/{repo}/releases/download/{tag}/{asset}` |
| **数据必经中继** | 客户端 HEAD + 每个分片均 `follow_redirects=True` → 最终响应永远来自中继 |
| 中继目前**零 API 调用** | 只做 `fetch(origin)` 代理 |
| 官方 `versions.json` **无哈希字段** | 仅 `{name, release_date, release_notes}` |
| 体积不是痛点 | 50,943 B → gzip 后 **2,371 B**，`cf-cache-status: HIT` |

## 方案选型

| 方案 | 额外请求 | 客户端改动 | 判定 |
|---|---|---|---|
| **A. 中继响应带 header** | 0（复用已有缓存） | 读 header + 比对 | ✅ **选它** |
| B. 解析端点 302 带 header | 0 | 需改 redirect 处理才能看到 | ❌ `follow_redirects=True` 会吞掉 302 的 header |
| C. 独立 `/sha256?...` 端点 | +1 | 多一次往返 | ❌ 中继已能给 |
| D. `versions.json` 加 per-asset 表 | 0 | 最简单 | ❌ 粒度错（per-version vs per-asset）、体积 ×3、`list -r` 白付费 |

**A 的核心优势**：客户端本来就打中继 → header **白拿、零额外往返**；
注入点唯一（`relayResponse`），一处覆盖 200/206/HEAD。

## 详细设计（worker 侧）

### D1 注入点：`relayResponse(request, resp)`

三条路径（CF 缓存命中 / 回源 / 错误）全部汇入此函数 → 单点注入：

```
解析 url.pathname → 取 repo, tag, asset（asset 需 decodeURIComponent）
→ 查 digest（D2）
→ 命中且以 "sha256:" 开头 → out.headers.set("x-gdpm-sha256", digest)
→ 否则省略
```

**关键决定：header 在"服务时"附加，不写进 30 天的资产缓存**

```
❌ 存入缓存: 首次若 API 失败 → 无 header 的响应被缓存 30 天 → 之后永远拿不到
✅ 服务时附加: 资产缓存保持干净，每次服务重查（CF 边缘缓存的 release JSON，亚毫秒）
```

命中缓存的请求也要做一次 digest 查找，但那是 `caches.default.match()`
（边缘本地），**无网络开销**。

### D2 digest 获取：复用 `fetchRelease(repo, tag)`

```
缓存键: gdpm-worker-cache/{repo}/releases/tags/{tag}   ← 与资产解析同一键
TTL:    3600s（API_CACHE_TTL）
命中:   JSON 里 assets.find(name === asset).digest
未命中: 同步调 GitHub API（200–400ms），失败 → null → 省略 header
```

- **配额成本**：与资产解析**共享缓存** → 走 API 解析路径时 **0 次额外调用**；
  走零配额 HEAD 试探路径时 **+1 次 / (repo,tag) / 小时**（对比未认证 60/时可忽略）
- **签名改动**：`relayGitHub(request, url, ctx)` 目前**无 `env`**，而 `fetchRelease`
  需要它（`GITHUB_TOKEN`）→ 调用点需多传 `env`

### D3 预热（建议加）

解析端点命中资产后已知 `repo`+`tag` → 顺手 `ctx.waitUntil(fetchRelease(repo, tag))`
后台预热。客户端从 302 跳到中继有 50–200ms 往返，后台 API 大概率先完成 →
中继首请求命中热缓存，**消掉 D2 的同步延迟**。未命中仍同步兜底（正确性优先）。

### D4 Header 规格

```
名称:   x-gdpm-sha256
值:     sha256:<64位小写hex>      ← 与 GitHub asset.digest 完全同格式
出现于: 中继的 200 / 206 / HEAD 响应
不出现: 502（上游失败，无字节）、digest 查不到时
```

- **保留 `sha256:` 前缀**：与源头一致便于排错，且算法带标签，将来 `sha512:` 可平滑扩展
- **不加 `x-gdpm-size`**：HEAD 的 `content-length` 已是资产大小（客户端现就读它算分片）

### D5 失败语义

| 情形 | header | 客户端策略（P2 阶段定） |
|---|---|---|
| digest 命中 | ✅ | 必须比对，**不匹配 → 失败** |
| API 403 限流 / 404 / 网络错 | ❌ | 建议**告警但不中断**（API 故障不应让安装不可用） |
| 资产名在 JSON 中找不到 | ❌ | 同上 |
| `digest` 缺失或非 `sha256:` | ❌ | 同上 |

**不设 `unavailable` 标记**：剥离该 header 需攻破客户端↔镜像 TLS——与伪造文件
是同一威胁，TLS 已覆盖；加标记只增加协议面。

### D6 边界情况

| # | 情形 | 处理 |
|---|---|---|
| 1 | 资产名 URL 编码（`encodeURIComponent` 生成） | 查找前 `decodeURIComponent` 再比对 |
| 2 | Range 206（不入缓存，逐片回源） | 同样附加——服务时查，无额外成本 |
| 3 | 完整 GET 命中 30 天缓存 | header 服务时附加，缓存体保持干净（D1） |
| 4 | `godot-builds` vs `godot` 双仓库 | 路径里 repo 明确，无需猜测 |
| 5 | 404 tag（短缓存 null 路径） | 省略 header |
| 6 | 上游 502 | 走 `json(502,...)`，不经过 `relayResponse`，天然无 header |

## 安全边界（诚实版）

```
防:   传输损坏 / 边缘缓存文件污染（不同缓存键）/ 中继返回错误版本（CRC32 检不出）/ worker bug
不防: worker 运营者同时伪造文件与 digest（信任域同源）/ GitHub 上游同时替换两者
```

- 与 PyPI/pip、npm、cargo 的 checksum **同性质**：完整性校验（integrity），
  非来源认证（provenance）
- Godot 不签 GPG，GitHub digest 是可得的最好来源
- **相对 zip 自带 CRC32 的增量**：① **版本错配检测**（CRC 只证明"这个 zip 内部
  自洽"，不证明"它是对的版本"）② 密码学强度（CRC32 是 32 位非密码学，可构造碰撞）
- "同源拿哈希防不住同源作恶"——但 worker 与 gdpm 同作者，**信任域本就相同**，
  真实威胁是非恶意的损坏与 bug
