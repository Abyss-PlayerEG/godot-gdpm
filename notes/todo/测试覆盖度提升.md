## 二、解读

- **典型 CLI 形态**：基座 84% vs 命令层 36%。命令层网络+IO+渲染纠缠，mock 成本高是主因
- **高覆盖区全是重构驱动**（help/i18n/download/config——重构时补的测试）；老业务流
  （add/sync/lock）无人动过就无测。覆盖是历史活动的副产品，不是风险评估的结果
- **真风险**：`add`(10%) + `installer/manager`(15%) + `zip`(12%)——用户必经之路，出 bug 直接砸每个用户

## 三、计划

- [ ] **P0 `utils/version.py`** — 版本语义地基（70 语句仅 14 被测）；纯函数易测，性价比最高
- [ ] **P0 `utils/zip.py`** — zip-slip 安全测试（与质量与安全加固 todo 联动，做完顺手推进那条）
- [ ] **P1 `installer/manager.py` + `cli/commands/add.py`** — 核心业务路径；
      骨架复用现有 `test_install_guards.py` / `test_install_progress.py` 的 monkeypatch 模式
- [ ] **P2 `utils/path.py` + `utils/platform.py`** — 共 25 语句，白送
- [ ] 可选：`pytest-cov` 加入 dev 组 + `check.py` 增加 coverage gate
      （先低阈值如 45%，防倒退，随补测逐步上调——阈值定太高会逼出凑数测试）

## 四、测试约定（AGENTS.md 已有，补测时遵守）

- mock 网络 → patch 精确的 `httpx` 调用点；隔离文件 → `tmp_path`；**永不碰真实 `$HOME`**
- 一个测试只测一个行为；优先扩现有 test 文件而非新建
